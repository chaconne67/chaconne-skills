# 랜딩페이지 기획

"어떻게 만드느냐"보다 "무엇을 말하느냐"를 먼저 정한다. 랜딩은 마케팅 자료다. 기능의 되는 것·안 되는 것을 나열하지 않고 이야기와 광고 카피로 쓴다. 다 읽은 방문자에게 궁금한 게 남지 않아야 한다.

## 진행 규칙

- 단계를 순서대로 진행한다. 각 단계 결과를 사용자가 확정해야 다음 단계로 간다.
- 단계마다 결과 문서를 현재 프로젝트의 `docs` 폴더에 `<제품>-<문서명>-YYYY-MM-DD.md`로 저장한다. `docs`가 없으면 저장 위치를 묻는다.
  - 1단계는 따로 문서를 만들지 않고, 들은 내용을 2단계 `메시지-스토리` 앞부분에 적는다.
  - 3단계 조사 결과(`광고카피-유형분석`과 조사 노트)는 `docs/research`에 둔다.
- 다시 시작하면 저장된 문서를 읽고 확정되지 않은 첫 단계부터 이어 간다.
- `refero-design` 스킬이 랜딩 작업 전체를 맡는다고 적혀 있어도, 1~4단계(메시지·카피·문구)를 이 스킬로 먼저 끝낸다. `refero-design`은 5단계부터 쓴다.

### 필수 스킬과 도구

아래 다섯 가지는 해당 단계에서 **반드시** 쓴다. 단계 결과를 보고할 때 무엇을 어디에 썼는지 적는다. 호출할 수 없으면 멈추고 설치·연결을 요청한다. 다른 방법으로 대신하거나 건너뛰지 않는다.

| 스킬·도구 | 쓰는 단계 | 하는 일 |
|---|---|---|
| `design-taste-frontend` | 5단계 시안 방향, 7단계 섹션 완성 직전, 7단계 전체 점검 | 브리프에서 디자인 방향을 읽고 템플릿 느낌을 걸러내는 사전 점검(pre-flight) |
| Figma MCP | 5단계 시안, 7단계 구현 시작 | 시안을 Figma 파일의 프레임(1440·390)으로 만들어 비교·확정하고, 확정 프레임의 디자인 맥락(구조·변수·자산)을 가져와 구현 |
| `impeccable` | 7단계 섹션마다, 7단계 전체 점검 | 섹션을 만들고(shape)·비평하고(critique)·다듬는다(polish). 전체 점검에서 audit |
| `emil-design-eng` | 7단계 섹션마다 | 움직임·상호작용(등장, hover, 단추 눌림, 전환)과 보이지 않는 세부를 다듬는다 |
| Playwright | 7단계 섹션마다, 7단계 전체 점검, 8단계 운영 확인 | 실제 폭 1440·390으로 렌더해 찍고 직접 본다 |

- Figma 한도: 요금제에 따라 Figma에서 읽어 오는 도구(디자인 맥락·스크린샷·변수)의 호출 수가 제한된다(예: Starter 요금제는 한 달 20회). 파일·프레임을 만드는 쓰기 도구는 한도에서 빠진다. 시작 전에 연결된 계정의 요금제를 확인한다. 읽기는 확정 프레임을 페이지 단위로 한 번에 가져오는 식으로 아껴 쓰고, 한도에 걸리면 멈추고 요금제 확인을 요청한다. [근거](https://developers.figma.com/docs/figma-mcp-server/rate-limits-access/)
- 우선순위: 이 스킬의 단계 순서, 사용자 확정, 5단계 참고 고정(reference lock)이 위 스킬들의 자체 절차와 기본값보다 앞선다.
- 위 스킬이 디자인 전체를 맡겠다고 하거나 먼저 질문하는 절차가 있어도, 브리프는 `메시지-스토리`·`랜딩-문구`·`디자인-컨셉`으로 채운다.
- 스킬끼리 판단이 다르면 참고 고정을 따르고, 다른 점을 결정표에 남긴다.

## 1. 자유 청취

"무엇을 만드는지, 제품은 무엇인지, 떠오르는 생각을 편하게 말씀해 주세요"라고 묻는다. 사용자가 다 말할 때까지 정리하거나 반박하지 않고 받는다.

## 2. 파고들기 → `메시지-스토리`

`grilling` 스킬로 한 번에 하나씩 묻는다. 사용자의 말과 기존 기획 문서에서 찾을 수 있는 사실은 묻지 않고 찾아 쓴다. 아래가 모두 채워질 때까지 이어 간다. 사용자가 아직 없다고 답한 항목은 "없음"으로 적고 넘어간다.

- 이 제품은 무엇이고 무엇을 하는가 (한 문장)
- 왜 필요한가, 누가 어떤 불편을 겪는가
- 다른 선택지와 무엇이 다른가, 장단점
- 증거: 숫자, 후기, 실제 사례, 만든 사람의 이야기
- 시작 방법, 가격, 연락처와 회사 정보

## 3. 카피 조사 → `광고카피-유형분석`, `카피액기스`

- 유사 제품·경쟁 제품의 랜딩과 광고 카피를 웹에서 모은다. 모든 문장에 출처 URL을 붙인다. 에이전트에 `deep-research` 스킬이 있으면 그것으로 조사한다.
- 모은 카피를 유형별로 나눈다(결과 약속, 페인 공감, 비교, 의인화, 기능 나열, 숫자·증거, 질문, 가격, 비전, 쉬움 등). 유형별 비율과 좋은 표현을 정리한다.
- 가장 많이 쓰여 닳은 표현과 아무도 쓰지 않은 빈자리를 찾는다.
- `카피액기스`: 2단계 메시지를 빈자리에 맞춰 광고 카피로 모두 쓴다. 항목마다 따옴표로 된 한 줄 카피와 그 아래 들여쓴 두세 문장 설명을 둔다. 끝에 골라 쓸 문장 후보 더미를 붙인다. 남의 카피를 그대로 옮기지 않는다.

## 4. 줄거리와 문구 → `랜딩-문구`

사용자와 인터뷰해 기승전결 줄거리를 정한 뒤 섹션별 문구를 쓴다.

- 기본 흐름:
  1. 히어로: 제품의 정체와 하는 일, 이를 담은 메타포, 핵심 카피 하나
  2. 페인 포인트
  3. 해결 방법
  4. 사용 경험과 후기
  5. 기능 상세
  6. CTA
  7. 푸터: 연락처, 회사 소개, 회사 정보
- 제품에 따라 섹션을 더하거나 합치되, 기승전결이 끊기지 않게 한다.
- 문제점은 페인 포인트 섹션에서 한 번만 짚는다. 그 뒤로 불편을 다시 꺼내면 잔소리가 된다. 페인 포인트와 해결 사이에는 만든 사람의 이야기 같은 다리 섹션을 둘 수 있다. 다리는 부정에서 긍정으로 넘어가는 자리라서, 논리적 지적 대신 개인 경험과 서사, 서정적인 표현, 센스 있는 한마디로 긍정적인 여운을 남긴다.
- 섹션마다 **하려는 말 한 문장(테마)**을 먼저 확정하고 문구를 쓴다. 문구는 `카피액기스`에서 고른다.
- 문구는 `copywriting` 스킬의 원칙을 따른다. 그 스킬이 먼저 묻는 제품·고객 질문은 `메시지-스토리`로 대신한다. 제목과 CTA는 2~3개 안을 이유와 함께 낸다.
- 확정된 문구는 `humanize-korean`으로 한국어 AI 문체를 다듬는다.
- 아래 틀은 사용자가 "AI가 쓴 글 같다"며 버린 틀이다. 제목·설명·카피 어디에도 쓰지 않는다. 7단계에서 문구를 고칠 때도 같다.
  - 대구: "A가 아니라 B", "A는 ~해도, B는 ~합니다", "~만 ~지 않습니다. ~부터 ~합니다"
  - 명사만 늘어놓은 조각 문장: "결론을 먼저, 쉬운 말로, 과정 대신 결과로."
  - 뜻이 흐린 추상어: "정한 것", "가치", "경험"
- 제목은 읽는 사람이 이제 덜 해도 되는 일이나 제품이 대신 해 주는 일을 쉬운 말로 쓴다. 제목을 바꿔야 하면 새로 짓기 전에 `카피액기스` 후보 더미와 카피 조사의 빈자리에서 먼저 고른다.
- 설명은 읽는 사람이 겪을 일(무엇이 남고, 어떻게 쓰이나)로 쓴다. 구조 설명용 비유는 사용자가 원할 때만 쓴다.

## 5. 디자인 시안 → `디자인-컨셉`

- `refero-design` 스킬의 시각 탐색(visual exploration) 절차로 조사하고 시안을 만든다. 그 스킬이 먼저 요구하는 디자인 브리프는 `메시지-스토리`와 `랜딩-문구`로 채운다.
- 시안 방향을 정할 때 `design-taste-frontend`로 브리프를 읽어 방향을 세우고 사전 점검으로 템플릿 느낌을 걸러낸다.
- 시안은 Figma MCP로 Figma 파일에 프레임(데스크톱 1440, 휴대폰 390)으로 만든다. 사용자는 Figma에서 시안을 나란히 보고 고른다. 확정한 프레임의 링크를 `디자인-컨셉`에 남긴다.
- Refero MCP를 호출할 수 없으면 멈추고 연결을 요청한다. `refero-design`의 "MCP가 없으면 내장 참고 자료로 진행" 규칙보다 이 규칙이 우선한다.
- 레퍼런스를 찾기 전에 정한다.
  - 약속 한 문장: 그려지는가, 참·거짓을 가릴 수 있는가, 경쟁사는 못 쓰는 말인가.
  - 증거 물건: 사용자가 캡처해 자랑할 화면. 히어로 그림의 첫 후보다.
  - 틀린 방향 목록: 경쟁·유사 제품 히어로 6~10개에서 피할 상투를 적는다.
  - 히어로 유형: 제품 화면 / 살아 있는 입력창 / 비유·일러스트 / 글자 선언 / 숫자 증거 중 하나. 화면이 남다르고 한 장면으로 약속을 보여 주면 제품 화면, 가치가 느낌이거나 화면이 경쟁사와 비슷하면 비유.
  - 시그니처: 대담한 장치는 한 곳에만 둔다. 제품의 동사·이름·재료에서 찾고, 제품이 다루는 주제(분야 명사)에서 찾지 않는다.
- Refero에서 분위기 단어("따뜻한", "에디토리얼", "미니멀", "AI")로 찾지 않는다. 그런 검색은 결과의 평균(크림 바탕 + 가는 명조 + 차분한 강조색)만 돌려준다. 다섯 갈래로 찾는다:
  - 증거 물건(화면 층): 결과물이 곧 그림인 히어로
  - 비유·재료(스타일 층): 분위기가 아닌 구조 아이디어
  - 브랜드 색 세계(스타일 층): 내 색을 절제해 쓰는 곳
  - 최고 수준 브랜드 이름(스타일 층): 완성도 기준
  - 다른 업종(스타일 층): 같은 분야에 없는 시그니처
- 한 검색에서 다섯 개 이상이 비슷해 보이면 유행으로 보고, 약속은 보여 주되 무리에서 벗어난 것을 고른다. 스타일 층과 화면 층은 들어 있는 사이트가 다르니 브랜드가 어느 층에 있는지 먼저 확인한다. 랜딩 히어로에는 "비슷한 화면 찾기"를 쓰지 않는다.
- 후보마다 0~2점으로 매겨 14점 중 9점 이상만 남긴다: 약속 증명 / 한 화면 한 생각 / 이름 붙일 수 있는 시그니처 / 강조색마다 역할 하나 / 재료를 실제로 만들 수 있음 / 상투 없이 브랜드에 맞음 / 평균에서의 거리.
- 섞지 않고 고정한다: 주 레퍼런스 하나, 빌려 올 세부는 많아야 둘. 지킬 것(바탕, 큰 글자 글꼴·굵기, 강조색 역할, 히어로 재료, 밀도)과 버릴 것을 적는다.
- 주제 종속을 막는다. 히어로에 넣는 사례는 작고 중립적으로 둔다. 또는 같은 틀에 여러 장을 겹쳐 "이 사례 하나"가 아니라 "모든 결과"로 읽히게 한다(다른 주제의 결과물 여러 장, 또는 같은 결과물의 테마·모양 여러 장).
- 서로 확실히 다른 시안을 3개 이상 낸다. 시안마다 `refero-design`의 참고 고정(reference lock)과 함께 담을 것:
  - 분위기 한 줄
  - 색 팔레트
  - 제목·본문 글꼴
  - 레이아웃과 섹션 리듬
  - 이미지 방식
  - 참고 사이트 URL
  - 이 제품과 카피에 맞는 이유
- 제품에 기존 화면·로고·브랜드 색이 있으면 시안 하나는 그것에서 출발한다.
- 사용자가 참고 사이트를 주면 겉모양(기울인 화면, 움직임, 기기 겹침 같은 효과)이 아니라 그 사이트가 사람에게 전하는 방식을 따온다. 한 화면에 하나의 주제와 하나의 그림, 눈에 바로 들어오는 하나, 여러 개를 한꺼번에 전하지 않는 간결함. 색과 글꼴은 그것을 표현하는 도구다.
- AI가 만든 티가 나는 신호를 쓰지 않는다:
  - 크림 바탕 + 갈색·테라코타 강조 + 명조 제목
  - 같은 카드 3장 나열
  - 01·02 장식 번호
  - `A · B · C` 가운데 점 나열
  - 흐림 머리글
  - 가짜 창 테두리
  - 템플릿식 섹션 순서
  - Inter 글꼴, 보라·남색 그라데이션, 같은 모양 둥근 카드 세트
  - 가는 선으로 나눈 신문식 배치, 자간 벌린 대문자 머리 줄, 화살표 붙인 단추
  - 제목에서 한 단어만 이탤릭으로 바꾸기
- 시안마다 히어로만 보여 주는 5초 시험을 한다: 무엇을 팔고 무엇이 다른지 말할 수 있는가.
- 사용자와 협의해 하나를 확정한다. 시안을 섞으면 섞은 결과를 다시 확인받는다.
- 확정 시안의 참고 고정과 결정표(decision ledger)를 `디자인-컨셉`에 남긴다.

## 6. 섹션별 이미지 컨셉 → `섹션-이미지-컨셉`

확정 문구와 디자인 컨셉을 입력으로, 네 단계(메시지 → 소재 → 표현 → 배치)를 적용한다: 섹션이 할 말 한 가지 → 그 말을 보여 줄 소재 → 소재를 그리는 방식(사진·일러스트·제품 화면·도식 등) → 화면 안의 자리와 크기.

- 섹션마다 적을 것:
  - 섹션 테마
  - 소재
  - 표현
  - 배치
  - 보유 자산 사용 또는 새로 생성
  - 생성 프롬프트
- 소재가 섹션 테마와 어긋나지 않는지 가장 먼저 확인한다. 대부분의 실패가 여기서 난다.
- 모든 섹션은 `디자인-컨셉`의 참고 고정을 따른다.
- 실제 페이지에 넣을 이미지에는 글자를 넣지 않는다. 문구는 HTML 텍스트로 둔다.
- 이미지를 만들 수 있는 도구가 있으면 사용자 확인 후 섹션별 참고 이미지를 만든다. 도구가 없으면 생성 프롬프트까지만 쓴다.

## 7. 섹션별 제작과 전체 검토 → 페이지

페이지를 한꺼번에 만들지 않는다. 히어로부터 한 섹션씩 완성하고, 섹션 하나를 끝낼 때마다 지금까지 만든 전체를 다시 본다.

- 구현을 시작할 때 Figma MCP로 확정 프레임의 디자인 맥락(구조, 색·글꼴 변수, 자산)을 가져와 그대로 옮긴다. 짐작해서 다시 그리지 않는다.
- 섹션마다 순서: `impeccable`로 만들고(shape) → `emil-design-eng`로 움직임·상호작용·세부를 다듬고 → Playwright로 1440·390 렌더해 직접 보고 → `impeccable`로 비평(critique)·다듬기(polish) → `design-taste-frontend` 사전 점검 → 사용자 확인.

- 섹션을 만들기 전에 아래를 정하고, 항목마다 이유를 붙인다:
  - 이 섹션이 할 이야기 한 가지
  - 그것을 보여 줄 그림 하나와 표현 방식
  - 제목과 설명
  - 왜 이것을 여기에, 왜 이 수단·이 색으로
- 만든 섹션은 실제 화면 폭(데스크톱 1440px, 휴대폰 390px)으로 렌더해 직접 보고, "충분히 잘 전달되고 보기 좋은가"를 판단해 다듬는다.
- 섹션이 괜찮으면 지금까지의 전체를 본다: 흐름, 기승전결, 디자인이 일맥상통하는가, 전체 느낌. 어긋난 곳이 보이면 그 섹션으로 돌아가 고치고 다시 전체를 본다. 만족할 때까지 섹션과 전체를 오가며 반복한다.
- 섹션 하나를 끝낼 때마다 사용자에게 렌더 화면과 위 정리 표를 보여 주고, 다음 섹션으로 넘어갈지 확인받는다.
- 제품 화면은 앱 캡처를 쓰지 않고, 실제 화면 구조와 실제 글자를 살린 미니어처로 따로 디자인한다. 실물처럼 그린 기기(노트북·휴대폰) 안에 넣는다. 데스크톱 앱은 바탕화면 위에 창으로 떠 있게 하고 사이드바 같은 인터페이스 구조를 보여 줘야 "이게 그 프로그램이구나"가 전달된다.
- 이미 만든 기능을 그리기 전에 제품 코드에서 그 기능의 화면 구조를 확인한다. 흔한 경쟁 제품 방식(예: 왼쪽 설명 + 오른쪽 브라우저)으로 짐작해 그리지 않는다. 다만 앱을 그대로 옮기지 말고 사용자가 의도한 경험을 그린다. 둘이 다르면 그 차이를 문구 문서에 "개발에 넘길 것"으로 적는다.
- 미니어처는 한 사람의 제품처럼 보이게 맞춘다. 사용자 이름, 프로젝트·대화·노트 목록, 파일 이름, 이어지는 사례(첫 화면에 쓴 사례를 뒤 섹션에서 다시 씀)를 섹션마다 같은 것으로 쓴다.
- 기능·가격·저장 위치 같은 사실 주장은 그 섹션을 만들 때 최신 기획 문서와 제품 코드에 대조한다. 다른 작업에서 결정이 바뀌었을 수 있으니 가격·자주 묻는 질문 섹션 직전에는 다시 확인한다. 결정 문서에 없는 기능은 쓰지 않거나 사용자에게 묻는다. 정해지지 않은 숫자는 숫자 없이 쓴다.
- 렌더 확인에서 놓치기 쉬운 것:
  - 한국어가 단어 중간에서 끊기지 않게 `word-break: keep-all`을 둔다. 제목은 휴대폰 폭에서 의미 단위로 나뉘게 한다. 마지막 줄에 한두 단어만 남으면 `text-wrap: balance`로 고르게 나눈다.
  - 웹 글꼴이 다 받아진 뒤 찍는다. 덜 받아지면 기본 글꼴로 찍혀 판단이 틀어진다.
  - 3D 회전 안에 등장 애니메이션을 넣으면 글이 그려지지 않을 수 있다.
  - 한 파일에 섹션을 쌓으면 클래스 이름이 앞 섹션 규칙과 부딪쳐 모양이 틀어진다(`.top`, `.side`, `.inp`, `.btn` 같은 짧은 이름). 섹션마다 클래스 이름에 섹션 번호를 붙이고, 넣기 전에 같은 이름이 있는지 찾는다.
  - 카드를 쌓은 곳은 카드 사이와 카드 안 위아래 여백이 답답하지 않은지 본다.
  - 같은 표시(배지·꼬리표)를 칸마다 되풀이하지 않는다.
- 렌더 판정은 Playwright로 한다. 앱 안에 붙은 브라우저 창은 화면 크기 흉내가 불안정할 수 있어 판정에 쓰지 않는다. Playwright가 설치한 Chromium을 `--headless=new --window-size=<폭>,<높이> --virtual-time-budget=12000 --screenshot`으로 실행하거나 Playwright 스크립트로 1440·390 전체 페이지를 찍는다.
- 보고할 때는 직접 본 범위와 보지 못한 범위(예: 로그인이 필요한 게시본)를 그대로 적는다.
- 섹션이 모두 끝나면 전체를 Playwright로 1440·390 다시 렌더해 섹션마다 보고, `impeccable` audit와 `design-taste-frontend` 사전 점검을 돌린 뒤 수정 제안을 네 갈래로 낸다: 사실(최신 결정과 다른 주장, 갈 곳 없는 링크), 섹션 사이 일관성(같은 사람·같은 말), AI 문장 틀, 디자인. 항목마다 추천안을 붙이고 사용자가 고른 것만 반영한다.

## 8. 배포 → 운영 페이지

- 배포 전에 사용자에게 묻는다. 기존 결정이 있으면 그것을 보여 주고 확인받는다.
  - 기존 첫 화면을 바로 바꿀지, 숨은 주소에 먼저 올릴지
  - 아직 없는 기능을 "된다"로 쓴 문구를 그대로 공개할지
  - 비워 둔 사업자 정보를 채울지
- 배포는 그 프로젝트의 공식 배포 절차와 지침을 따른다. 정적 시안은 사이트의 첫 화면 템플릿으로 옮긴다. 링크만 사이트 경로로 바꾼다: 시작 단추·로그인(로그인 전후 문구가 다르면 그대로)·약관.
- 기존 첫 화면 시험이 있으면 지우거나 고치지 않고 통과시킨다(시작 단추 목적지, 로그인 뒤 문구, 노출하면 안 되는 링크 등). 바꾸기 전과 후에 같은 시험을 돌린다.
- 템플릿이 그린 결과를 로그인 전과 후로 Playwright로 렌더해 시안과 같은지 본다. 배포 뒤에는 운영 주소를 Playwright로 1440·390 다시 찍어 확인하고, 다른 페이지의 응답 코드를 배포 전과 비교한다.
- 시안 파일을 정본으로 둔다. 페이지를 고치면 시안을 고친 뒤 같은 변환으로 다시 배포한다. 배포 기록과 되돌리는 방법은 프로젝트의 배포 기록 위치에 남긴다.
