# 영상 제작

사용자가 원하는 영상을 만든다. 에이전트가 혼자 그럴듯한 영상을 만들어 내미는 것이 목표가 아니다. 영상의 품질은 렌더보다 기획에서 정해진다. 렌더는 몇 번이든 다시 돌릴 수 있지만, 메시지·장면 구조·카피·디자인 규칙·음성·박자가 틀리면 처음부터 다시 만들어야 한다. 그래서 단계마다 사용자를 참여시키고, 확정을 받고 나서 다음으로 간다.

## 진행 규칙

- 단계를 순서대로 진행한다. 각 단계의 결과를 사용자가 확정해야 다음 단계로 간다.
- 영상 작업 폴더: 지금 작업하는 프로젝트 폴더가 있으면 그 아래 `video/`를 만들고, 없으면 작업 루트에 `<영상 이름>-video/`를 만든다. 영상 코드·대사·음성·음악·그림·결과물을 모두 이 폴더에 둔다. 내려받은 파일(음악·그림)은 받은 경로를 확인한 뒤 이 폴더의 `assets/` 아래로 옮긴다.
- 기획 문서는 프로젝트의 `docs`에 두고(없으면 영상 작업 폴더에), 영상 작업 폴더 위치를 적는다.
- 결과는 기획 문서 하나로 쌓는다: `<제품>-영상기획-<영상 이름>-YYYY-MM-DD.md`. 단계가 끝날 때마다 그 절을 채운다. 콘티가 길면 `<제품>-영상콘티-<영상 이름>-YYYY-MM-DD.md`로 나눈다. `docs`가 없으면 저장 위치를 묻는다.
- 다시 시작하면 그 문서를 읽고 확정되지 않은 첫 단계부터 이어 간다.
- **조사할 것과 물을 것을 나눈다.** 사실(제품이 하는 일, 화면, 숫자, 경쟁 영상, 시청자, 유행)은 에이전트가 찾는다. 취향·의도·결정(무엇을 왜 알리는지, 원하는 느낌, 받아들일 수 없는 것)은 사용자에게 묻는다. 찾을 수 있는 것을 묻지 않고, 사용자가 정할 것을 에이전트가 정하지 않는다.
- 묻는 방식은 `grilling` 스킬을 따른다: 한 번에 한 질문, 질문마다 추천 답과 이유를 붙인다.
- 사용자가 준 장면 아이디어는 방향 제안으로 받는다. 더 나은 안이 있으면 이유와 함께 제안하고 고르게 한다.
- 단계에 필요한 도구(im-not-ai, 음성 생성 키, 제작 도구)를 쓸 수 없으면 그 단계에서 멈추고 무엇이 왜 필요한지 알린다. 다른 방법으로 대신해 그 단계를 통과시키지 않는다. 대신한 결과는 사용자가 원한 품질 기준을 거치지 않은 것이기 때문이다.

### 함께 쓰는 스킬

| 스킬·도구 | 단계 | 하는 일 |
|---|---|---|
| `grilling` | 2, 4, 5 | 한 번에 하나씩 묻고 추천 답을 붙인다 |
| `deep-research`(있으면), 웹 검색 | 0, 3 | 제품·시청자·경쟁 영상·유행·카피 조사. 문장마다 출처 URL |
| `copywriting` | 4, 6 | 키워드와 문구를 광고 카피로 쓰는 원칙. 그 스킬의 제품·고객 질문은 기획 문서로 대신한다 |
| `refero-design` | 5 | 시각 레퍼런스 조사와 참고 고정(reference lock) |
| im-not-ai 최신판(`humanize-scan`, `humanize-korean`) | 4, 6, 10 | 키워드·대본·자막·화면 글의 AI 티 점검과 윤문. **반드시 쓴다**. 쓰기 전에 GitHub `https://github.com/epoko77-ai/im-not-ai` 최신 판과 설치 판을 비교하고, 설치 판(플러그인 목록이나 설치 폴더의 판 번호)이 낮거나 없으면 최신 판의 `skills/humanize-scan`·`skills/humanize-korean` 지시를 읽어 따른다 |
| `user-copy` | 6, 10 | 화면 글을 처음 보는 사람 입장에서 다시 읽기 |
| HyperFrames 공식 스킬(`hyperframes-core`·`-cli`·`-animation`·`-audio`) | 5, 7, 9 | HyperFrames 작성 계약과 명령. [제작: HyperFrames](references/production-hyperframes.md) |
| 이 스킬의 `scripts/`(Python 3, ffmpeg 필요) | 7, 8, 9 | 음성 생성(`lines.py`·`vo.py`), 박자 지도(`beats.py`), HyperFrames 장면 배치(`hyperframes/build.py`), 최종 인코딩(`encode.py`). 고치지 않고 부른다 |

- 이 스킬의 단계 순서·사용자 확정이 위 스킬들의 자체 절차보다 앞선다. 특히 HyperFrames 공식 스킬의 인터뷰(intent interview)·자체 승인 흐름은 쓰지 않고, 이 스킬의 기획 문서를 브리프로 준다.

## 0. 묻기 전에 조사

사용자에게 처음 묻기 전에 이미 있는 자료를 읽는다.

- 사용자가 준 파일·링크, 프로젝트 `docs`(기획·랜딩 문구·카피액기스·기존 영상 기획), 홈페이지, 앱 화면과 코드, 로고·색·글꼴·화면 캡처·기존 영상.
- 결과를 "알고 있는 것 / 아직 모르는 것"으로 정리해 보여 준다. 모르는 것 중 조사로 찾을 것과 물어야 할 것을 나눠 적는다([인터뷰](references/interview.md) 표).

## 1. 자유 청취

"어떤 영상을 만들고 싶은지, 떠오르는 대로 말씀해 주세요"라고 묻는다. 사용자가 다 말할 때까지 정리하거나 반박하지 않고 받는다.

## 2. 인터뷰 → 기획 문서 「요구」

[인터뷰](references/interview.md)의 항목이 모두 채워질 때까지 하나씩 묻는다. 0단계와 사용자 말로 이미 답이 나온 항목은 묻지 않는다.

- **형식을 맨 먼저 정한다**: 숏폼(세로)인지, 일반 영상(가로)인지, 스토어 미리보기인지, 사용법 시리즈인지. 형식에 따라 화면비·길이·첫 몇 초·자막·안전 영역이 모두 달라진다.
- 목적(본 뒤 시청자가 할 일), 대상, 게시처, 핵심 메시지, 톤, 넣을 것·뺄 것, 소리 취향, 일정과 승인자.
- 사용자가 아직 정하지 않았다고 하면 "미정"으로 적고, 그 항목이 막는 단계 앞에서 다시 묻는다.

## 3. 통할지 조사 → 「시청자·시장 조사」

에이전트가 깊게 조사한다. 사용자에게 묻지 않는다.

- **시청자**: 누구이고, 이 문제를 어떻게 겪고, 어떤 말을 쓰고, 이 채널에서 영상을 어떻게 보는가(소리 켜고 보는지, 몇 초 안에 넘기는지).
- **같은 채널의 경쟁·유사 영상** 10편 안팎: 구조, 길이, 첫 장면, 카피, 무엇이 반응을 얻었는가(조회·댓글 같은 공개 근거만).
- **최근 유행**: 그 형식(숏폼·제품 소개)에서 지금 자주 쓰이는 구성과 표현, 그리고 닳아서 피할 것.
- **카피 조사**: 경쟁·유사 제품의 영상·광고 카피 20~40개를 출처와 함께 모으고, 유형(결과 약속, 페인 공감, 비교, 숫자·증거, 질문, 의인화, 기능 나열 등)으로 나눠 비율을 센다. 가장 닳은 표현과 아무도 쓰지 않은 빈자리를 찾는다. 남의 카피를 그대로 옮기지 않는다.
- 끝에 판단을 쓴다: 2단계 메시지가 이 시청자에게 통할지, 통하려면 무엇을 바꿔야 할지, 근거는 무엇인지. 사용자가 메시지를 확정한다.

## 4. 장면 나누기와 핵심 키워드 → 「장면 키워드」

**이 스킬에서 가장 중요한 단계다.** 장면마다 핵심 키워드가 잘 서면 콘티는 거기서 풀려 나온다. 키워드가 흐리면 콘티·대본·디자인이 모두 흔들린다. 자세한 절차와 점검표는 [장면 키워드](references/keywords.md).

- 영상을 장면으로 나누고, 장면마다 적는다:
  - **핵심 키워드**: 그 장면이 시청자 머리에 남길 말 하나(짧은 낱말이나 구)
  - **테마 한 문장**: 그 장면이 하려는 말
  - **시청자 질문**: 이 장면이 답하는, 그 순간 시청자가 품은 질문 하나
  - **근거**: 3단계 카피 조사의 빈자리, 확인한 사실
- **키워드는 카피 스타일로 정한다.** 3단계에서 고른 빈자리와 메시지가 겹치는 곳에서 키워드를 뽑고, 조사에서 효과가 있던 카피의 결(길이·말투·구체성)에 맞춘다.
- **서사를 점검한다.** 키워드만 이어 읽어도 이야기가 되는가, 시청자 질문이 자연스럽게 다음 질문을 낳는가, 감정이 정한 흐름(예: 공감 → 신뢰 → 납득 → 행동)을 따르는가, 문제는 한 번만 짚는가.
- **카피라이터로 점검한다.** 키워드마다 그림이 그려지는가, 경쟁사도 그대로 쓸 수 있는 말은 아닌가, 시청자의 말인가, 시청자가 덜 해도 되는 일을 말하는가.
- 키워드 목록을 im-not-ai `humanize-scan`으로 한 번 잰다(AI 틀이 키워드 단계에서 들어오면 대본 전체로 번진다).
- 표로 보여 주고, 사용자와 고쳐 가며 확정한다. 확정 전에는 5단계로 가지 않는다.

## 5. 디자인 컨셉 → 「디자인 컨셉」

에이전트가 레퍼런스를 찾아 서로 확실히 다른 안을 3개 이상 내고, 사용자가 고른다.

- **먼저 제작 도구를 고르고 프로젝트를 만든다.** 대표 장면 정지 그림(아래)부터 실제 도구로 그리기 때문이다. 기본은 HyperFrames다. 새 영상, 키네틱 타이포가 많은 영상, 웹 화면을 그리는 영상에 쓴다. 이미 Remotion으로 만든 프로젝트를 잇는 경우나 앱의 React 부품을 그대로 가져와야 하는 경우에만 Remotion을 쓴다. 고른 도구와 이유를 기획 문서에 적고, 한 영상 안에서 두 도구를 섞지 않는다. 준비 방법: [제작: HyperFrames](references/production-hyperframes.md), [제작: Remotion](references/production-remotion.md).

- 레퍼런스: 같은 채널의 잘 된 영상, 사용자가 좋다고 한 영상, `refero-design`의 스타일 조사, 제품 홈페이지. 레퍼런스마다 **가져올 것·뺄 것·이유**를 표로 적는다. 겉모양(기울인 화면, 3D, 겹친 기기)이 아니라 사람에게 전하는 방식(한 화면에 한 생각, 무엇을 고정하고 무엇을 움직이는지)을 가져온다. 레퍼런스마다 맡을 역할은 하나다(예: 제목 움직임만, 떠 있는 카드만). 섞어서 평균을 내지 않는다.
- 안마다 담을 것:
  - 톤 형용사 두 개
  - 색과 각 색의 역할(정보 색, 상태 색, 강조 색), 배경
  - 서체와 크기 체계
  - 정보 모드(설명 중: 배경 고정, 보여 줄 것만 움직임)와 전환 모드(장면 사이: 그림만, 정보 없음)의 모양
  - 전환 종류(여러 개를 돌려 씀), 움직임의 성격(튕김 여부, 속도), 키네틱 타이포를 쓸지와 어디에
  - 음악 분위기와 템포, 한 곡으로 갈지 장마다 곡을 바꿀지
  - **대표 장면 정지 그림** 한 장(제작 도구로 실제로 그려 찍은 것). 앱 화면이 들어가는 장면이면 그 화면의 미니어처를 이때 먼저 만든다(8단계와 같은 방법)
  - 참고 사이트·영상 URL과 이 제품·키워드에 맞는 이유
- 제품에 기존 화면·로고·브랜드 색이 있으면 안 하나는 그것에서 출발한다.
- 사용자가 고른다. 섞자고 하면 섞은 결과를 다시 그려 확인받는다. 확정안의 참고 고정과 "하지 않을 것" 목록을 문서에 남긴다.

## 6. 콘티와 대본 → 「콘티」, 윤문

- 장면 키워드 표에서 장면마다 콘티를 펼친다: 화면 글, 동작(무엇이 어떤 순서로 움직이는가), 내레이션, 자막, 시연 문장, 효과음, 근거(제품 화면이면 코드 위치 `파일:줄`이나 실제 화면).
- 시각(초)은 적지 않는다. 목소리 길이와 음악 박자가 정한다(9단계).
- 제품 화면이 나오면 콘티를 쓰기 전에 실제 화면을 본다. 창 비율·문구·단추·동작·플랫폼 모양을 하나하나 대조한다. 짐작으로 그리지 않는다. 앱을 실행하거나 접속하는 방법·시험 계정은 그 프로젝트 지침(`AGENTS.md` 등)에서 찾고, 없으면 사용자에게 묻는다.
- 시연 문장은 그 기능이 잘 드러나는 문장으로 쓴다. 사용자의 실제 개인 자료·고객 정보는 화면에 넣지 않는다.
- **윤문 (반드시)**: 내레이션·자막·화면 글·끝 문구 전부를 im-not-ai 최신판으로 점검하고 윤문한다.
  - 먼저 `humanize-scan`으로 재고, 고칠 것이 있으면 `humanize-korean`으로 윤문한다. 사실·숫자·고유명사·키워드는 바꾸지 않는다.
  - 내레이션의 쉼표는 목소리의 쉼이다. 쉼표 신호(C-11)가 걸려도 내레이션에서는 쉼으로 둘 수 있다. 같은 문장을 자막으로 띄울 때는 쉼표를 뺀다.
  - 이어서 `user-copy`로 처음 보는 사람 입장에서 읽는다: 모르는 말을 풀었는가, 보이는 것을 다시 말하지 않는가.
  - 사용자가 "AI가 쓴 것 같다"며 버린 틀은 쓰지 않는다: "A가 아니라 B" 대구, 명사만 늘어놓은 조각 문장, "경험·가치·솔루션" 같은 추상어, 동사 세 개 나열.
- 대본(윤문 전후 대조)과 콘티를 보여 주고 확정받는다.

## 7. 시험 장면과 소리 샘플

전체를 만들기 전에 확인받는다.

- 시험에 필요한 만큼만 8단계 준비를 먼저 한다: 그 장면의 대사 음성, 음악 후보의 박자 지도. 방법과 경로는 8·9단계와 같다(시험용 다른 경로를 만들지 않는다). 음악 없이 가기로 하면 정한 템포의 고정 간격 박자 지도를 만들어 같은 박자 계획을 쓴다.
- 대표 장면 하나를 실제로 렌더한다(박자·전환·키네틱 포함).
- 목소리 후보 2~3개, 말 속도 2~3가지(예: 원래·1.3배), 음악 후보를 들려준다. 음악은 두 길을 함께 제시한다: 사용자 계정의 Suno로 새로 만들기(추천, 저작권이 가장 깔끔함)와 YouTube 오디오 보관함에서 고르기. 사용자가 직접 받은 파일을 올려 줘도 된다. 권리 조건, 받아 오는 법, 여러 곡을 장면 전환에서 바꾸는 법은 [오디오](references/audio.md). 음악 없이 갈 수도 있다.
- 사용자가 "이 방식으로 진행"이라고 확정해야 8단계로 간다. 여기서 정한 것은 모든 장면에 그대로 쓰인다.

## 8. 준비

- 화면 부품: 공용 부품을 한 곳에 둔다(색, 박자 격자, 전환, 끝 카드, 앱 미니어처). 여러 편이면 복사하지 않고 같은 부품을 쓴다.
- 앱 화면은 캡처를 줄여 붙이지 않고 실제 구조와 실제 글자로 다시 그린 미니어처로 만든다. 먼저 실제 화면을 실제 크기로 찍은 참조 그림을 모으고(찍는 방법은 그 프로젝트 지침, 웹 화면은 헤드리스 브라우저로 실제 크기 캡처), 앱의 화면 코드(HTML·CSS·컴포넌트)에서 구조·문구·색을 가져와 같은 비율로 다시 그린다. 참조 그림과 나란히 놓고 대조한다.
- 코드로 그릴 수 없는 그림만 이미지로 만든다. 출처를 파일 옆에 적는다.
- 대사 원문은 한 파일에 둔다 → 음성 생성 → 낱말 시각까지 받는다.
- 음악 → 박자를 실측한 박자 지도. 효과음과 출처.
- 자세한 값과 명령: [오디오](references/audio.md), [제작: HyperFrames](references/production-hyperframes.md), [제작: Remotion](references/production-remotion.md).

## 9. 제작

- 5단계에서 고른 도구로 만든다.
- 실행 경로는 하나다: 대사 → 음성 → 박자 계획 → 장면 작성 → 렌더 → 인코딩(−16 LUFS). 고칠 때는 이 경로의 해당 단계를 고친다. 손 보정이나 따로 만든 편집본으로 얻은 결과는 성공이 아니다.
- 모든 장면 변화는 박자에 놓는다. 장면 길이는 목소리 길이를 박자로 올려 정한다.
- 여러 편이면 한 편을 끝까지 만들어 확인받은 뒤 나머지를 같은 방식으로 만든다.

## 10. 점검

[점검](references/checks.md)의 소리·화면·내용·문구 네 갈래로 본다.

- 장면표(일정 간격 캡처를 한 장에 모은 것)로 화면을 보고, 빠른 동작과 접합부는 프레임을 따로 본다.
- 소리는 그림으로 대신 판정하지 않는다. 측정할 수 있는 것(말끝 잘림, 겹침, 음량)은 에이전트가 재고, 귀로만 알 수 있는 것(음색 흔들림, 자연스러움)은 사용자에게 들어 봐 달라고 요청한다.
- 정상 속도로 처음부터 끝까지 재생해 보는 것도 사용자에게 요청한다. 에이전트가 직접 볼 수 없는 항목은 "확인 못 함"으로 적고 통과로 쓰지 않는다.
- 결과와 고칠 목록(장면·시각·근거·고칠 방법)을 사용자에게 보여 주고, 사용자가 고른 것을 모아서 고친다. 고친 뒤 처음부터 다시 점검한다.
- 실패 항목이 없거나, 남은 항목을 사용자가 그대로 두기로 하면 11단계로 간다.

## 11. 배포

- 검토본은 사용자가 휴대폰으로도 볼 수 있는 경로(클라우드 드라이브의 프로젝트 폴더 등)로 보낸다.
- 공개·스토어 교체·홈페이지 반영은 그 직전에 사용자의 "예"를 받는다. 게시 대화상자는 단추 이름을 읽고 한 단계씩 누른다(같은 자리의 "다음"이 "게시"로 바뀐다).
- 게시 위치·판 번호·날짜를 기획 문서에 남긴다.

## 제작 원칙 (사용자 피드백에서 나온 것)

- **전환과 정보를 나눈다.** 설명하는 동안 배경은 고정하고 보여 줄 것만 움직인다. 장면 사이 전환은 그림으로만 바뀌고 정보를 싣지 않는다. 다음 제목은 전환 뒤에 나온다.
- **템포가 빠른 것과 리듬이 없는 것은 다르다.** 빠르게 가도 모든 변화는 박자·마디에 떨어진다. 읽을 시간과 쉼을 남긴다.
- **실제와 맞아야 한다.** 제품 화면은 창 비율·문구·동작까지 실제와 대조한다. "예전과 같음"으로 넘기지 않는다.
- **레퍼런스는 철학을 가져온다.** 겉모양 효과를 베끼지 않는다.
- **캡처 대신 미니어처.** 실제 구조와 실제 글자로 보기 좋게 다시 그린다.
- **한 편 안에서는 같은 것을 같게.** 같은 목소리, 같은 창 위치, 같은 색 역할.
- **바꿀 수 있는 것은 바꿀 수 있다고 보인다.** 명령어·설정 값처럼 사용자가 바꿀 수 있는 것을 고정된 것처럼 보이지 않는다.
- 움직임 기법(가감속, 시간차, 준비 동작, 장면 연결, 키네틱 타이포)은 [모션 기법](references/craft/methods.md)에서 필요한 절만 읽는다.
